# คู่มือทำความเข้าใจระบบ

เอกสารนี้อธิบาย **เหตุผลเบื้องหลังการออกแบบ** ของแต่ละส่วน เหมาะกับการใช้เขียนรายงาน
หรือเตรียมนำเสนอ ถ้าต้องการแค่วิธีใช้งาน ให้อ่าน [README.md](../README.md) แทน

## 1. ทำไมต้องใช้ landmark แทนรูปภาพ

นี่คือการตัดสินใจที่สำคัญที่สุดของโปรเจค และเป็นจุดที่ต่างจากโปรเจคต้นแบบมากที่สุด

### ปัญหาของการเทรนจากรูปภาพโดยตรง

ถ้าเราป้อนรูปมือ 300×300 พิกเซลให้โมเดล สิ่งที่โมเดลเห็นคือตัวเลข 270,000 ค่า
(300 × 300 × 3 สี) ซึ่งปะปนข้อมูลที่ **ไม่เกี่ยวกับความหมายของท่ามือเลย** มาด้วยมหาศาล:

- สีผิวของผู้ทำท่า
- สีและลวดลายของเสื้อผ้า
- ฉากหลังในห้อง
- สภาพแสง เงา และอุณหภูมิสีของหลอดไฟ

โมเดลไม่รู้ว่าอะไรสำคัญอะไรไม่สำคัญ มันจึงเรียนรู้ทุกอย่างพร้อมกัน ผลคือถ้าเก็บข้อมูล
ในห้องหนึ่งแล้วเอาไปใช้อีกห้องหนึ่ง ความแม่นยำจะตกฮวบ เพราะโมเดลเผลอไป
"จำฉากหลัง" แทนที่จะจำท่ามือ ปัญหานี้เรียกว่า **spurious correlation**

การจะสู้กับปัญหานี้ด้วยวิธีเทรนจากภาพ ต้องใช้ข้อมูลจำนวนมหาศาลที่หลากหลายพอ
จนโมเดลสรุปได้เองว่าฉากหลังไม่สำคัญ — ซึ่งเกินกำลังของโปรเจคระดับนักเรียน

### ทางออก: ให้ MediaPipe กลั่นข้อมูลให้ก่อน

MediaPipe HandLandmarker ผ่านการเทรนมาแล้วด้วยข้อมูลมือหลายล้านภาพ
หน้าที่ของมันคือแปลงรูปภาพให้เหลือแค่ **จุดสำคัญบนมือ 21 จุด**

```
รูปภาพ 270,000 ค่า  ->  MediaPipe  ->  จุด 21 จุด × 3 แกน = 63 ค่า
   (มีขยะปนเยอะ)                          (เหลือแต่รูปทรงมือล้วน ๆ)
```

เท่ากับเราได้ยืมความรู้จากโมเดลที่ Google เทรนมาแล้วมาใช้ฟรี ๆ
(แนวคิดนี้เรียกว่า **transfer learning**) และที่สำคัญที่สุด — พิกัดจุดไม่มีข้อมูลสี
สีผิว เสื้อผ้า และฉากหลังจึงหายไปตั้งแต่ขั้นตอนนี้

## 2. Feature engineering — หัวใจของโปรเจค

โค้ดส่วนนี้อยู่ที่ [`src/features.py`](../src/features.py)

จุด 21 จุดที่ได้จาก MediaPipe ยังใช้ตรง ๆ ไม่ได้ เพราะค่าพิกัดยังขึ้นอยู่กับสองอย่าง
ที่ไม่เกี่ยวกับความหมายของท่ามือ:

| สิ่งรบกวน | ตัวอย่างปัญหา |
|-----------|----------------|
| **ตำแหน่ง** | ทำท่า "ก" มุมซ้ายบน กับมุมขวาล่าง ได้ตัวเลขคนละชุด |
| **ขนาด** | ทำท่า "ก" ใกล้กล้อง กับไกลกล้อง ได้ตัวเลขคนละชุด |

ถ้าไม่จัดการ โมเดลจะต้องเรียนรู้ท่าเดียวกันซ้ำ ๆ ในทุกตำแหน่งและทุกระยะ
สิ้นเปลืองข้อมูลมหาศาลโดยไม่จำเป็น

### วิธีแก้ — normalize สองขั้นตอน

**ขั้นที่ 1: ย้ายข้อมือไปที่จุดกำเนิด** (ตัดผลของตำแหน่ง)

```python
centered = points - points[0]   # points[0] คือข้อมือ
```

ทุกจุดถูกวัดเทียบกับข้อมือแทนที่จะเทียบกับมุมจอ มืออยู่ตรงไหนของเฟรมก็ได้ค่าเดิม

**ขั้นที่ 2: หารด้วยระยะที่ไกลที่สุดจากข้อมือ** (ตัดผลของขนาด)

```python
scale = np.linalg.norm(centered, axis=1).max()
normalized = centered / scale
```

มือใหญ่หรือเล็ก ใกล้หรือไกลกล้อง ก็ถูกย่อ/ขยายให้อยู่ในมาตราส่วนเดียวกัน

> **ข้อนี้ตรวจสอบได้จริง** — `selftest.py` ข้อที่ 4 ทดสอบโดยเลื่อนจุดทั้งชุด
> และคูณขนาด 2.5 เท่า แล้วยืนยันว่าค่าที่ normalize แล้วยังเท่าเดิมทุกตัว

### ประกอบเป็นเวกเตอร์ความยาวคงที่ 133 ค่า

โมเดล machine learning รับ input ขนาดตายตัว แต่จำนวนมือที่เห็นในแต่ละเฟรม
ไม่แน่นอน (0, 1 หรือ 2 ข้าง) จึงต้องจองช่องไว้ล่วงหน้า:

```
[--- ช่องมือซ้าย 64 ค่า ---][--- ช่องมือขวา 64 ค่า ---][ท่อนคู่มือ 5 ค่า]
 63 พิกัด + 1 ธงบอกการมีอยู่  63 พิกัด + 1 ธงบอกการมีอยู่   ความสัมพันธ์ของสองมือ
```

ถ้าเห็นมือข้างเดียว อีกช่องเป็นศูนย์ทั้งหมด และธงเป็น 0
**ธงบอกการมีอยู่มีความสำคัญ** เพราะช่วยให้โมเดลแยกได้ว่า "ไม่มีมือ"
ต่างจาก "มีมือแต่พิกัดบังเอิญเป็นศูนย์"

### ท่อนคู่มือ — ราคาที่ต้องจ่ายของการ normalize

การ normalize ข้างบนเทียบแต่ละมือกับ **ข้อมือของมือข้างนั้นเอง** ซึ่งให้ผลดีมาก
แต่มีผลข้างเคียงที่มองข้ามง่าย: เมื่อทุกมือถูกย้ายไปที่จุดกำเนิดหมด ข้อมูลว่า
**สองมืออยู่ห่างกันแค่ไหน** ก็หายไปด้วย

ผลคือท่า "สองมือประกบกัน" กับ "สองมือแยกห่างกันสุดแขน" ได้เวกเตอร์เหมือนกันเป๊ะ
ทั้งที่เป็นคำละคำในภาษามือไทย จึงต้องเก็บส่วนที่หายไปกลับมาอีก 5 ค่า:

| ค่า | เก็บอะไร |
|-----|----------|
| `Pair_offset_x/y/z` | เวกเตอร์จากข้อมือซ้ายไปข้อมือขวา หารด้วยขนาดมือเฉลี่ย |
| `Pair_scale_balance` | `(ขนาดขวา - ขนาดซ้าย) / (ขนาดขวา + ขนาดซ้าย)` บอกว่ามือไหนอยู่ใกล้กล้องกว่า |
| `Pair_present` | ธงบอกว่าสี่ค่าข้างบนวัดมาจริง ไม่ใช่ศูนย์เพราะไม่มีข้อมูล |

ที่ต้องหารด้วยขนาดมือเฉลี่ยเพราะถ้าใช้ระยะดิบ ยืนไกลกล้องขึ้นค่าจะเล็กลงทันที
เมื่อหารด้วยขนาดมือ ทั้งตัวตั้งและตัวหารหดลงพร้อมกัน อัตราส่วนจึงคงเดิม —
เป็นหลักการเดียวกับที่ใช้ normalize รูปทรงมือ

> **ข้อนี้ตรวจสอบได้จริง** — `selftest.py` สร้างสองมือรูปทรงเดิมเป๊ะที่ระยะห่าง
> ต่างกัน แล้วยืนยันสองเรื่อง: ท่อน 128 ค่าแรกเหมือนกันทุกตัว (ยืนยันว่าข้อจำกัดนี้
> มีจริง) และเวกเตอร์เต็มต่างกัน (ยืนยันว่าท่อนคู่มือแก้ได้จริง)

## 3. Data augmentation แบบกลับด้านกระจก

ท่ามือส่วนใหญ่ทำด้วยมือซ้ายหรือขวาก็สื่อความหมายเดียวกัน เราจึงสร้างข้อมูลเพิ่ม
ได้ฟรีเท่าตัวด้วยการกลับด้าน — ทำสองอย่างพร้อมกัน:

1. สลับเครื่องหมายแกน x ของทุกจุด
2. สลับช่องมือซ้าย ↔ ช่องมือขวา

ประโยชน์คือโมเดลไม่ยึดติดว่าต้องใช้มือข้างไหน คนถนัดซ้ายกับถนัดขวาใช้ได้เหมือนกัน

### กับดักที่ต้องระวัง — data leakage

ใน [`src/train.py`](../src/train.py) เรา **แบ่งชุดเทรน/ชุดทดสอบก่อน แล้วค่อยเพิ่มข้อมูล**
ลำดับนี้สำคัญมาก ถ้าเพิ่มข้อมูลก่อนแล้วค่อยแบ่ง ภาพกลับด้านของตัวอย่างเดียวกัน
อาจไปโผล่ทั้งในชุดเทรนและชุดทดสอบ เท่ากับโมเดลเคยเห็นข้อสอบมาก่อน
คะแนนที่ได้จะสูงเกินจริงและเชื่อถือไม่ได้เลย

นี่เป็นความผิดพลาดที่พบบ่อยมากในโปรเจค machine learning ระดับเริ่มต้น

## 4. จากผลทายรายเฟรม สู่ประโยค

โค้ดส่วนนี้อยู่ที่คลาส `SentenceBuilder` ใน [`src/translate.py`](../src/translate.py)

กล้องส่งภาพมาราว 30 เฟรมต่อวินาที ถ้ารับทุกผลที่โมเดลทายได้
ข้อความจะกลายเป็น `สวัสดีสวัสดีสวัสดีสวัสดี...` ภายในวินาทีเดียว
และช่วงที่มือกำลังเปลี่ยนจากท่าหนึ่งไปอีกท่าหนึ่งก็จะถูกทายมั่วเป็นคำอื่นปนเข้ามา

จึงต้องมีตัวกรองสามชั้นทำงานเรียงกัน:

| ชั้น | กลไก | แก้ปัญหาอะไร | ค่าตั้ง |
|------|-------|---------------|---------|
| 1. ความมั่นใจ | ทิ้งผลที่ความน่าจะเป็นต่ำกว่าเกณฑ์ | ท่าที่ไม่ได้ตั้งใจทำ / ช่วงมือเปลี่ยนท่า | `CONFIDENCE_THRESHOLD` |
| 2. ความนิ่ง | ต้องทายคำเดิมติดกันครบ N เฟรม | ผลกระพริบไปมาระหว่างสองคำ | `STABLE_FRAMES_REQUIRED` |
| 3. ช่วงพัก | หลังรับคำแล้วไม่รับคำเดิมซ้ำทันที | คำเดียวถูกนับหลายรอบ | `COOLDOWN_SEC` |

ผู้ใช้จะเห็นชั้นที่ 2 เป็นแถบความคืบหน้าใต้คำที่กำลังทาย — ทำให้รู้ว่าต้องค้างท่าอีกนานแค่ไหน
ซึ่งดีกว่าปล่อยให้เดาเอง

> `selftest.py` ข้อสุดท้ายทดสอบตัวกรองทั้งสามชั้นนี้ครบทุกกรณี

### การปรับจูน

- **ทายผิดบ่อย / คำมั่วหลุดเข้ามา** → เพิ่ม `CONFIDENCE_THRESHOLD` (เช่น 0.85)
  หรือเพิ่ม `STABLE_FRAMES_REQUIRED` (เช่น 12)
- **ทำท่าถูกแล้วแต่ระบบไม่ยอมรับ** → ลด `CONFIDENCE_THRESHOLD` (เช่น 0.6)
  แต่ถ้าต้องลดต่ำกว่านี้ แปลว่าปัญหาอยู่ที่ข้อมูลไม่พอ ควรกลับไปเก็บเพิ่มดีกว่า
- **คำเดียวถูกนับซ้ำ** → เพิ่ม `COOLDOWN_SEC`

## 5. การแสดงผลภาษาไทย

`cv2.putText` ของ OpenCV รองรับเฉพาะตัวอักษร ASCII ถ้าส่งภาษาไทยเข้าไปจะได้
เครื่องหมาย `?` เรียงกันเป็นแถว นี่เป็นข้อจำกัดที่ทำให้โปรเจคภาษามือของไทยหลายอัน
ต้องยอมแสดงผลเป็นภาษาอังกฤษแทน

ทางแก้ใน [`src/thai_text.py`](../src/thai_text.py) คือ:

```
เฟรม OpenCV (BGR)  ->  ภาพ Pillow (RGB)  ->  วาดด้วยฟอนต์ไทยจริง  ->  กลับเป็น BGR
```

ระบบจะไล่หาฟอนต์ไทยตัวแรกที่มีในเครื่องจากรายการใน `config.py`
(เครื่องนี้ใช้ Leelawadee UI) และแคชฟอนต์ไว้ตามขนาดด้วย `lru_cache`
เพื่อไม่ให้ต้องโหลดไฟล์ฟอนต์ใหม่ทุกเฟรม ซึ่งจะทำให้ FPS ตก

## 6. อ่านรายงานผลการเทรน

หลังรัน `run train` จะได้ไฟล์ `docs/training_report.txt`

### Confusion matrix

ตารางที่มีประโยชน์ที่สุดในรายงาน — **แถว = คำที่ทำจริง, คอลัมน์ = คำที่โมเดลทาย**

ตัวเลขบนแนวทแยงมุมคือจำนวนที่ทายถูก ตัวเลขนอกแนวทแยงมุมคือความสับสน
ถ้าเห็นตัวเลขสูงผิดปกติที่ช่องใดช่องหนึ่งนอกแนวทแยง แปลว่าท่ามือสองท่านั้น
คล้ายกันเกินไปในสายตาของโมเดล วิธีแก้:

1. เก็บข้อมูลของสองคำนั้นเพิ่ม โดยเน้นความหลากหลายของมุมมอง
2. ถ้ายังสับสนอยู่ ให้พิจารณาว่าท่าทั้งสองต่างกันที่ **การเคลื่อนไหว** หรือเปล่า
   ถ้าใช่ ระบบเฟรมเดียวแยกไม่ออกแน่นอน ต้องไปทางโมเดลลำดับเวลา (ดูข้อ 7)

### precision กับ recall

- **precision ต่ำ** สำหรับคำหนึ่ง = โมเดลชอบทายคำนี้ทั้งที่ไม่ใช่
- **recall ต่ำ** สำหรับคำหนึ่ง = ทำท่านี้แล้วโมเดลมักทายเป็นคำอื่น

## 7. ข้อจำกัดเชิงสถาปัตยกรรม และก้าวต่อไป

**ระบบนี้ตัดสินใจจากเฟรมเดียวโดด ๆ** จึงจำแนกได้เฉพาะ "ท่านิ่ง" (static gesture)
ท่าที่รูปมือเหมือนกันแต่ทิศทางการเคลื่อนไหวต่างกัน ระบบจะแยกไม่ออกโดยสิ้นเชิง

ภาษามือไทยจริง ๆ ใช้ทั้งการเคลื่อนไหวของมือ ตำแหน่งของมือเทียบกับลำตัว สีหน้า
และการเคลื่อนไหวของศีรษะเป็นส่วนหนึ่งของไวยากรณ์ ระบบนี้จับได้เพียงมิติเดียว
จากหลายมิติ จึงควรเรียกว่า **ระบบจำแนกท่ามือ** มากกว่า **ระบบแปลภาษามือ**
— ความแม่นยำในการใช้คำนี้สำคัญเวลาเขียนรายงาน

### ก้าวต่อไปที่ทำให้ระบบอ่านการเคลื่อนไหวได้

แทนที่จะส่งเวกเตอร์ 133 ค่าของเฟรมเดียวเข้าโมเดล ให้สะสมไว้เป็นลำดับ:

```
เฟรมที่ 1  ->  [133 ค่า]  ─┐
เฟรมที่ 2  ->  [133 ค่า]   │
   ...                      ├─>  โมเดลลำดับเวลา (LSTM / GRU / 1D-CNN)  ->  คำ
เฟรมที่ 30 ->  [133 ค่า]  ─┘
```

สิ่งที่ต้องแก้:
- `collect.py` — บันทึกเป็นคลิปสั้น 30 เฟรมต่อ 1 ตัวอย่าง แทนเฟรมเดียว
- `train.py` — เปลี่ยนจาก `MLPClassifier` เป็นโมเดลลำดับเวลา (ต้องใช้ TensorFlow หรือ PyTorch)
- `translate.py` — เก็บ buffer แบบเลื่อนหน้าต่าง 30 เฟรมล่าสุดไว้ทำนาย
